# Trove v0.5.0 — Identity, Accounts & Security Foundation

## Product decision
Trove now treats the user account as a first-class product layer. The target flow is search → compare → book → My Trove → repeat booking, rather than a catalog that always sends users away.

## Authentication
- registration requires at least one contact: email or phone;
- login accepts email or phone;
- passwords are hashed with Node.js scrypt and unique salts;
- server-side sessions are stored behind a repository boundary and exposed through an HttpOnly cookie;
- sessions expire after 30 days and can be revoked;
- password reset invalidates existing sessions.

## Verification
- email/phone verification token model;
- password reset token model;
- tokens are stored as SHA-256 hashes;
- tokens expire after 15 minutes and are single-use;
- demo verification/reset codes are exposed only when NODE_ENV is not production.

## Security controls
- login/register/verification/reset rate limits;
- generic authentication failure response;
- CORS with credentials and explicit frontend origin;
- server-side session lookup;
- user data returned without password hashes;
- security audit events without passwords, OTPs or session IDs;
- account ownership is designed to be enforced at the API layer.

## Marketing
Email and SMS marketing consent are separate fields from contact information. Registration does not imply marketing consent.

## Frontend
- real login/register flows;
- contact verification page;
- password recovery/reset pages;
- account page;
- authenticated header state.

## Production hardening still required
The current demo repository uses in-memory storage so the project remains runnable without external infrastructure. Before production, replace it with PostgreSQL/Redis repositories, connect a transactional email/SMS provider, add a dedicated CSRF strategy for the final deployment topology, centralize schema validation, add MFA for privileged accounts, enforce HTTPS/HSTS, and add automated security tests.
