# Trove v1.0.4 — Order Recovery & Operations

## Delivered
- Provider booking attempt history with immutable-style attempt records.
- Attempt lifecycle: started / succeeded / failed / unknown.
- Exponential retry scheduling with a 3-attempt ceiling.
- Recovery endpoint for bookings that failed at the provider boundary.
- Explicit manual-review state in the recovery response instead of unsafe duplicate booking.
- Payment webhook handler with event-id idempotency.
- Payment webhook updates booking payment state atomically at the application boundary.
- Provider order IDs remain the strongest protection against duplicate provider orders.

## New endpoints
- POST `/api/bookings/:id/recover`
- GET `/api/me/bookings/:id/attempts`
- POST `/api/payments/webhooks/mock`

## Operational principle
If payment succeeded but provider booking returned an unknown outcome, Trove must reconcile before attempting another order. The demo implementation schedules recovery; a production provider adapter should implement `getBooking(orderReference)` and reconciliation against the provider.
