# Trove v1.1.0 — Production Booking Foundation

This release starts the transition from the v1.0.x in-memory booking prototype to production infrastructure.

## Added

- PostgreSQL connection pool with transaction helper.
- Redis client with health check.
- Redis-backed idempotency primitive with in-memory development fallback.
- Redis-backed distributed lock primitive with safe token release and in-memory development fallback.
- PostgreSQL initial schema for:
  - users and sessions;
  - verification tokens;
  - bookings and idempotency;
  - booking lifecycle events and attempts;
  - payment intents and payment events;
  - provider orders;
  - promotion usage;
  - audit events.
- Local `docker-compose.yml` for PostgreSQL 17 and Redis 8.
- `db:migrate` script using `psql`.
- `/api/health` now reports PostgreSQL and Redis configuration/connectivity.

## Important architecture decision

The current domain services still use the v1.0.x in-memory stores. This is intentional for this incremental release: the persistence boundary is introduced first, while behavior remains stable.

The next v1.1.x step should migrate the critical stores one by one behind repository interfaces, starting with:

1. auth users/sessions;
2. bookings + booking events + attempts;
3. payment intents + payment events;
4. promotion usage;
5. audit events.

After that, the in-memory stores can be removed from production mode.

## Local start

```bash
cd backend
docker compose up -d
export DATABASE_URL=postgresql://trove:trove_dev_password@localhost:5432/trove
export REDIS_URL=redis://localhost:6379
pnpm db:migrate
pnpm dev
```

Windows PowerShell:

```powershell
$env:DATABASE_URL='postgresql://trove:trove_dev_password@localhost:5432/trove'
$env:REDIS_URL='redis://localhost:6379'
pnpm db:migrate
pnpm dev
```

## Production notes

- Do not use the development PostgreSQL password in production.
- Use managed PostgreSQL and Redis with private networking/TLS.
- Store secrets outside the repository.
- Keep connection pool sizes within the managed database limits.
- Payment webhooks must be verified against the raw provider request body.
- Card data must never be stored by Trove.
