# Trove v1.1.2 — Booking Repository Migration

## Goal
Move the booking lifecycle from process-local in-memory state to the PostgreSQL persistence boundary, while preserving the existing booking orchestration and development fallback.

## Implemented
- `bookingStore` now uses PostgreSQL when `DATABASE_URL` is configured.
- In-memory fallback remains available for local development without PostgreSQL.
- Durable booking records.
- Durable booking idempotency records with a database primary key.
- Durable booking lifecycle events.
- Durable provider booking attempts.
- Booking ownership checks remain in the service/API layer.
- Booking recovery now reads attempts from PostgreSQL.
- Payment services can update durable booking payment state.
- Existing booking orchestrator continues to own business transitions.

## Database tables used
- `bookings`
- `booking_idempotency`
- `booking_events`
- `booking_attempts`

## Production direction
The booking domain is now restart-safe when PostgreSQL is enabled. A process restart no longer removes bookings, lifecycle events, idempotency records or provider attempts.

The next persistence migration is `v1.1.3 — Payment Repository Migration`, because payment intents/events must also survive process restarts before Trove should be exposed to real customers.

After that, the production hardening sequence is:

```text
Auth → PostgreSQL
Booking → PostgreSQL
Payment → PostgreSQL
Provider order → PostgreSQL
        ↓
Redis sessions / locks / rate limits / idempotency
        ↓
real PSP
        ↓
Booking.com sandbox
        ↓
production observability + deployment
```
