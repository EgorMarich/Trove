# Trove v0.4.0 — Offer & Booking Boundary

## Delivered

- Provider failures are isolated with `Promise.allSettled`; one unavailable source no longer breaks the whole search.
- Search response now exposes `providers`, `requestedProviders`, and per-provider status/capabilities.
- Backend price validation endpoint: `GET /api/tours/:id/price?provider=...`.
- Backend redirect boundary: `GET /api/tours/:id/redirect?provider=...`.
- Tour details now come from the API with a demo fallback and preserve provider metadata.
- Tour detail page now shows provider/source metadata, price freshness, trip details and recommendation reasons.
- CTA now validates the price before redirecting to the provider.
- Search page received loading skeletons, empty state and source/price messaging.
- Frontend API types now include provider capabilities, source URLs and price timestamps.

## Real integration direction

Booking.com Demand API currently supports content-only, search/look/redirect and search/look/book flows for supported services; access requires Managed Affiliate Partner status, Partner Centre access, an API key and Affiliate ID. Its sandbox supports accommodation search, availability and booking flows.

The Trove provider boundary is intentionally compatible with both redirect-first and native-booking integrations. This lets Trove start with a lower-complexity redirect model and later add native booking where commercial/API access permits.
